## Project Overview

Atomic Momentum is a habit tracking application:
- **Flutter app** (primary, long-term): Dart/Flutter for iOS, macOS, Android and web, on `main`. The goal is an App Store and Google Play release. Swift is written only where Apple requires it (widget, Live Activity and Watch extensions inside `ios/`).
- **SwiftUI app** (fallback): a native Xcode project on the `swift` branch, kept in case the project ever moves to Swift. Currently Xcode's starter template.
- **Web prototype** (retired): the original HTML/JS app with a Python server was removed from `main` on 2026-10-17. It's kept on the tag `legacy-web-prototype` (`git checkout legacy-web-prototype` to look at it).

The project focuses on helping users build and maintain positive daily habits with visual progress tracking, streak monitoring, and category-based organization.

## Architecture Overview

### Flutter Application Structure (Primary - Clean Architecture)
- **Entry Point**: `lib/main.dart` with dependency injection initialization
- **Domain Layer**: `lib/domain/` - Business logic and entities
  - `entities/` - Core data models (Habit, StreakData, HabitColor, etc.)
  - `usecases/` - Business logic operations (CreateHabit, UpdateHabit, etc.)
  - `repositories/` - Abstract data access interfaces
- **Data Layer**: `lib/data/` - Data sources and implementations  
  - `repositories/` - Concrete repository implementations
  - `datasources/` - SharedPreferences and local storage
  - `models/` - Data transfer objects
- **Presentation Layer**: `lib/presentation/` - UI and state management
  - `providers/` - State management (HabitProvider, CategoryProvider, ThemeProvider)
- **Core Layer**: `lib/core/` - Cross-cutting concerns
  - `injection/` - Dependency injection with GetIt
  - `validation/` - Business rule validation
  - `migration/` - Data migration utilities
  - `theme/` - iOS-specific styling

### Key Components
- **Habit Management**: Complete CRUD with validation and error handling
  - ✅ **Create**: Full habit creation with name, target, units, color, category, frequency
  - ✅ **Read**: Professional habit display with progress tracking and completion states
  - ✅ **Update**: Edit functionality with form pre-population and comprehensive validation
  - ✅ **Delete**: Safe deletion with confirmation dialogs and user feedback
- **Calendar View**: Monthly calendar with habit completion visualization and category filtering. On a day before a habit was being tracked (`Habit.startedOn`, from `Habit.trackedFrom`), the habit is listed last and grayed (`_NotStartedRow`, "Added Oct 10") and isn't counted in the day's rings or "X of Y done"; "Start from this day" asks (wording differs for habits being broken: the days since count as clean) and moves its start (`Habit.startFrom` / `HabitProvider.startFrom`, which pins the reset day so periods keep their boundaries). Logging a day before the start (from the habit page) also moves the start there for good, so clearing that log doesn't move it back. The confirmation has Undo. Editing a habit (one-page form and Story) has "Counts from" (`CountsFromSection`, `HabitDraft.countFrom`): earlier or later; a later day can't come after a logged one, so it asks to clear those first (`Habit.countFrom`, `Habit.clearBefore`, `HabitProvider.countFrom`)
- **Category System**: User-editable categories (`Category` entity + `CategoryRepository`, rules in `ManageCategoriesUseCase`); six built-ins seeded on first launch with ids `body`, `spirit`, … that habits store as `categoryId`; Settings → Categories (or long-press the rings) to add/edit/reorder/delete/restore; deleted or unknown ids show as Uncategorized. Design: `docs/design/custom-categories.md`
- **Streak Tracking**: Streaks are derived from per-day history (`StreakCalculator`), counted in days/weeks/months, with the "never miss twice" rule: one missed due period is bridged (the streak is `atRisk` and the card says "Don't miss twice"), two in a row end it. Editing a past day on the Calendar repairs or breaks a streak. Stored streaks are recomputed on load (`UpdateHabitUseCase.resetHabitsIfNeeded`)
- **Momentum**: a 0–100 score per habit (`MomentumCalculator`, `Habit.momentum`): an exponential moving average over due periods with partial credit, calibrated to reach 80 (`Momentum.habitFormed`, "habit formed") in ~66 days of steady practice on any schedule; a two-minute period never lowers it (holds it, or lifts it toward 50). Levels (`MomentumLevel`): Building 0–39, Rolling 40–69, Strong 70–79, Unstoppable 80–89 (from habit formed), Atomic 90+. Shown on the card with a 7-day trend arrow; the Habits ring (`MomentumRing`, the average of tracked habits, `HabitProvider.overallMomentum`) has a mark at 80 and its level, and tapping it explains momentum. For charts use `MomentumCalculator.series` / `Habit.momentumSeries` (one pass), not `momentumAt` per day
- **Reset Days**: Weekly/monthly habits reset on a user-chosen weekday/day-of-month (`Habit.resetAnchor`); progress rolls over at local midnight
- **Streak Warnings**: `StreakWarningPlanner` plans a "Don't miss twice" notification before the miss that would end a streak (default 4 hours ahead, configurable in Settings), plus an optional nudge before a first miss (Settings switch); `StreakWarningService` schedules them
- **Smart Reminders**: `ReminderSettings` (smart or custom days, time, message); `ReminderPlanner` works out times from the schedule (each due day for daily habits; a countdown to the due day for longer periods: 1 day before for every 2–6 days, 3 and 1 day before for weekly to every 3 weeks, 7/3/1 for monthly) and drops reminders once the period is done; `ReminderService` schedules the soonest 48 across habits as one-off notifications (iOS allows 64) and replaces them on load, changes, progress and midnight. New habits remind by default at Settings → Default time; `smart_reminders_migration.dart` switched them on once for older habits
- **Two-minute version**: a habit's tiny version for hard days (`TwoMinuteVersion`: description, optional minimum amount, "Show on card"). The card's "2 min" button (`TwoMinuteButton`) or reaching the minimum keeps the day: streaks count it as kept, momentum never drops for it (`TwoMinuteLog`, used by both calculators), reminders and warnings stop for that period. Tapped days are stored apart from history in `Habit.twoMinuteDays`, for later statistics and rewards
- **Notification taps**: `NotificationService.handleTap` turns a payload into `focusRequests` (also on launch from a tap); `IOSMainNavigation` switches to Habits and pops to the list, `HomeScreen` clears a hiding filter, scrolls to the card and highlights it. The Habits list builds every card (a `Column`, not a lazy sliver) so any card can be scrolled to
- **Breaking a habit**: `Habit.goal` is build, quit (target 0: any slip breaks the day) or limit (target = most allowed per day/week/month). For a habit being broken a period is kept at or under the limit, nothing logged included, from the day it was first tracked; the day under way counts while under but can't make up for a slip before it (`StreakCalculator` `BreakRule`, `Habit.wasCompletedOnDate`); momentum gives 1 or 0 per period. Reminders become a daily check-in ("Still on track? Log any slips."), never dropped; no streak warnings. The editor's Build | Break pill (`GoalPill`, confirm each time) frames Story ("I will quit [smoking]", "I will keep [alcohol] to [2 drinks] [a day]") and Builder (break steps and quick picks); a habit's goal can't change once added. Cards show the room left (`Habit.roomLeftOn`), "Clean today"/"1 slip today" (`BreakWording`), + logs a slip, and the ring takes no tap or hold
- **Notifications**: each habit's `HabitNotify` (sound, time-sensitive, streak warnings), set in the editor's reminder section; Settings → Notifications has the default sound (Chime), quiet hours and "Time-sensitive alerts". Sounds are three original tones from `tool/make_sounds.py` (`ios/Runner/*.wav`, `android/.../res/raw/`); `NotificationService.detailsFor` builds iOS/Android details (Android: a channel per sound), and the schedulers resolve habits against `NotifyDefaults`. Time-sensitive needs the entitlement in `ios/Runner/Runner.entitlements` (enable the capability on the Apple Developer account). Quiet hours (`QuietHours.shift`): early notifications wait until they end, late ones come 15 minutes before they start, same day

### Data Flow (Clean Architecture)
1. UI triggers use cases through providers
2. Use cases execute business logic using repository interfaces
3. Repositories handle data persistence via SharedPreferences
4. State updates flow back through providers to UI
5. All data models support JSON serialization for cross-platform compatibility

### Small Screens and Text
The smallest supported phone is the **iPhone SE (2nd/3rd gen), 375pt wide**; the minimum iOS is 16. Every screen must work there at the default text size and at iOS's largest standard size (~135%), and must not break at Accessibility sizes.
- **Our labels are never cut off with "…".** Keep titles short (~20 characters or fewer); explanations go in subtitles and footers, which wrap.
- **Rows grow taller instead of truncating.** No fixed heights around text; use minimum heights. `CupertinoListTile` truncates titles by default: give text an explicit `maxLines` (see `settings_list.dart`).
- **User content** (habit and category names) may wrap to 2 lines; only beyond that may it end in "…".
- **Layouts adapt:** habit cards and Calendar rows switch to two rows below 390pt or above 115% text (`HabitCard.useTwoRows`); category rings show 4 per page with large text.
- **Guard:** `test/widget/small_screens_test.dart` renders every screen with real fonts (`test/helpers/real_fonts.dart`) at 375/390pt and 100%/135% text, and fails on any overflow or text that hits its line limit. Add new screens and sheets to it.

### Testing Strategy
- **Every feature or fix ships with tests.** Run the whole suite with `./flutter/bin/flutter test`; it must pass.
- **Layout**: `test/unit/` (pure logic, mirrors `lib/`), `test/integration/` (real use cases + SharedPreferences mock), `test/widget/` and `test/widget_test.dart` (screens)
- **Imports**: always `package:atomic_momentum/...`, never relative `../lib/` paths (relative imports load libraries twice and make coverage report ~0%)
- **Time**: app code reads the time with `clock.now()` from package:clock, never `DateTime.now()` (a guard test enforces it), so tests can run the app under `withClock`. Pure logic also takes a `now` parameter
- **Notification simulator** (`test/simulation/`): six weeks of the real app on a simulated clock, against a simulated iOS notification center (delivers as time passes, applies iOS's 64 limit). Every delivery is checked (nothing missing or extra versus the app's plan, nothing for a finished period, right times, warnings only with a streak at stake, no duplicates). Each scenario's timeline is saved in `test/simulation/goldens/`: review diffs, update with `./flutter/bin/flutter test test/simulation --update-goldens`. After changing reminders, warnings or dates, run `tool/notification_sim.sh` (UTC, New York, London, Lord Howe: clock changes); scenarios cover break-habit check-ins (11) and quiet hours (12). Add a scenario for each new kind of notification
- **On-device check**: `tool/device_notification_check.sh "<simulator>"` schedules real notifications seconds ahead and confirms iOS delivers them, then reinstalls the real app; run by hand on both simulators when notification code changes. Not `flutter test integration_test`, which uninstalls the app and its data
- **Year simulator** (`test/simulation/year/`): a year of use (`YearPersona`, `lib/core/dev/year_persona.dart`: twelve habits of every kind, a fortnight's holiday, edits, a deletion, Start from / Counts from, holds with Undo, Calendar backfills, notes, quotes, settings changes; deterministic, from seeded dice) lived through the real app on the simulated phone, Mon Oct 19 2026 to Mon Oct 18 2027. `Reference` (`reference.dart`) works out on its own, from a ledger of what was done, what every number should be: periods, streaks, momentum, the heatmap, Insights, achievements and the day each was reached, reminders that should come. After every visit and day (`year_run.dart`) the app must match it: streaks, momentum and trend, the card's bars, Calendar, the habit page, Insights, quotes, which achievement is celebrated (`AchievementCelebrations`, the same rules as the main screen), reminders expected from the ledger (beyond the per-delivery checks), and a cold start from storage on each 1st. `PersonaDriver` does the actions through the providers. The month-by-month digest (`goldens/year_digest.txt`) is the same in all four zones; problems are listed (each once, with a count) and written to `build/year_report.txt`. About 2 minutes; `YEAR_PROFILE=1` prints what's slow at a year. Planted bugs (two-minute lowering momentum, no monthly reminders, Calendar counting a habit before it began, a celebration not remembered) each fail it
- **The year on a device**: `tool/device_year_check.sh "<simulator or emulator-5554>" [days]` lives the same year in the real app on screen (`integration_test/year_on_device_test.dart`): the clock is simulated around the whole test (frames and timers read it), storage is in memory (the device's own habits are never touched), notifications go to the real notification center. One day a week the persona taps the cards (+, 2 min, hold and Undo); after every visit the cards' streak badges, VoiceOver labels and the momentum ring must match the `Reference`; at each month's end every screen is visited and screenshotted to `build/year_screens/<device>/` (`m01_habits.png` …); at the end the device's pending notifications must be exactly what the app planned. Puts the real app back afterwards. About 30 minutes for a year on an iPhone simulator; use fewer days on the slow Android emulator. Run it from a clean checkout (a worktree) when someone has unfinished native changes in the main folder
- **A year by hand**: Settings → Developer (debug builds) → "Load a year of use" (`YearOfUse`, `lib/core/dev/year_of_use.dart`) builds the persona's year ending today straight onto the habits (the year simulator checks it equals the lived year), keeping the person's habits, achievements and quotes aside under `dev_backup_v1`; "Put my habits back" restores them exactly. Settings are left alone
- **Notifications**: tests use fakes from `test/helpers/` (`FakeStreakWarningScheduler`, `FakeReminderScheduler`, `FakeNotificationsPlugin`)
- **Fonts and randomness**: widget tests draw text in a square placeholder font; tests about fit load real fonts (`real_fonts.dart`). `test/flutter_test_config.dart` seeds the greeting so layouts are the same every run
- **Async in widget tests**: don't keep a `Future` alive across calls in app code (chained futures break under the test clock); use a flag and a pending value instead (see `ReminderService.syncAll`)
- **Status (2026-10-18)**: 1361 tests passing, including the notification simulator and the year simulator (coverage last measured at 58.5% on 2026-10-15; use cases, data layer and `habit_provider.dart` were the weakest areas)

## Key Implementation Details
- **Storage**: habits are JSON in SharedPreferences via `SharedPreferencesDataSource`; a habit keeps its full per-day `history`, and streak, progress and momentum are derived from it (`Habit.refresh`, `StreakCalculator`, `MomentumCalculator`). Categories live under `categories_v1`; quotes of the person's own under `quotes_mine_v1`, saved quote ids under `quotes_saved_v1`; Health's last sync `health_last_sync_v1` and the app's own Health writes `health_writes_v1` (this phone's, never synced)
- **Dates**: day-only dates are built from calendar fields (`DateTime(y, m, d)`), never with `toLocal()`; table_calendar hands over UTC midnights
- **Notifications**: `NotificationService` wraps flutter_local_notifications. Reminders use payload `reminder|<habitId>` and are found and replaced as a set; streak warnings use ids hashed from `<habitId>-streak-…`. iOS keeps at most 64 pending: reminders get what streak warnings leave (`ReminderService.roomFor`). Warning lead times count on the clock (24h before midnight is midnight the day before, even when clocks change). Permission is asked once at first launch, after the first frame
- **Performance with a long history** (a mature user has a year or more of days per habit; keep it fast at two):
  - **Storage**: `SharedPreferencesDataSource` decodes once and keeps the models and each habit's JSON; a save serializes only the habits it changes and writes once (`saveHabits` batches; it re-reads if something else writes the key). Stored JSON of 64 KB or more is decoded in `Isolate.run`, and `UpdateHabitUseCase.refreshAll` (the launch's reset, returning every habit so it isn't decoded again) runs in `Isolate.run` from 1,500 history days, so the launch intro keeps drawing
  - **Caches** (all keyed by the `Habit` instance, so any change makes a new instance and drops them; keep `Habit` immutable): `late final` `schedule`, `_periodTotals`, `momentum`, `trackedFrom`, `_twoMinutePeriods`; `Insights.periods` (per period of now), `Insights._daysOf` and `_monthEnds` (per day), `Achievements._walk` and `_formedOn` (per day), `HabitStats.of` (per day and week start). `Achievements.earned`/`next` remember their last answer for the same habits (by identity), day and week start, which the main screen, Insights and the Achievements page share. Work over many periods goes through `periodsBack` and `Habit.periodOutcome` (one date sum per period), not `wasCompletedOnDate` per period
  - **Off the frame**: the main screen checks achievements after the frame that shows a change, once per batch of notifies; notifications are rescheduled only for what changed since the last sync (a full reload replaces them all)
  - **Measuring**: `test/performance/year_performance_test.dart` times a cold start, the first start of a day, a tap, and the first look at each history screen at one and two years (`--dart-define=PERF_PRINT=true` prints the table; debug VM numbers, so compare them with each other). `tool/perf_check.sh <android device> [years]` runs `integration_test/year_performance_test.dart` in profile mode (as it ships; the iOS simulator only runs debug) and prints wall and frame times. Measure on a quiet machine
- **Adding a screen or sheet**: use `LargeTitleScaffold` for main tabs (it clears the floating tab bar), the adaptive helpers for dialogs and pickers, and add it to `test/widget/small_screens_test.dart`
- **Platforms**: iOS and Android are the targets; `macos/` and `web/` are kept for development runs. **Android** builds and runs (since 2026-10-18): Android Gradle Plugin 8.12.1, Kotlin 2.2, Gradle 8.13, Java 17 (Homebrew `openjdk@17`), compileSdk 36, core library desugaring for flutter_local_notifications. The SDK is Homebrew's `android-commandlinetools` at `/opt/homebrew/share/android-commandlinetools` (Flutter is configured with it and the JDK); emulator `Momentum_Pixel` (Android 16): start it with `$ANDROID_HOME/emulator/emulator -avd Momentum_Pixel`, then `./flutter/bin/flutter run -d emulator-5554`. The manifest declares notification, exact-alarm and boot permissions and the plugin's receivers; where exact alarms aren't allowed (off by default from Android 14) notifications are scheduled inexactly instead of failing (`NotificationService._androidScheduleMode`). Notification sounds are kept in release builds by `res/raw/keep.xml` Linux and Windows runners were removed (recreate with `flutter create --platforms=linux,windows .`)
